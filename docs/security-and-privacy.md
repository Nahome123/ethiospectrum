# Security and privacy

## ETH-024 translation boundary

Translation authorization is exclusively the global content-editor or administrator role. It grants no household, dependent, document, roadmap, reminder, or private-profile access, and translation routes/actions do not load household context. Controlled functions derive actor, validate parent/locale/content/version, enforce different-user review, and audit atomically. Public callers receive reader-safe selected content only; workflow status, review notes, identities, versions, and audits remain editor-only.

## ETH-021 roadmap controls

Roadmap reads require an active household membership. Database functions derive `auth.uid()` and the active household, force RLS, revoke direct browser writes, and use a fixed empty search path. Owners and administrators can archive, restore, and reorder; members can create and update only their own or assigned active items and cannot assign another person; viewers read active items only. Mutations use an expected update timestamp to reject stale edits and an idempotency key to avoid duplicate creates. The roadmap does not access reminders, notifications, workers, provider credentials, or private document content.

Family, dependent, education, healthcare, benefit, and document information are sensitive. The current trust boundary is browser -> authorized server action/API -> Supabase with RLS -> private storage. Service-role credentials stay server-side. Signed URLs are short-lived; document content is never placed in source control, logs, analytics, test fixtures, or prompts beyond an authorized runtime request.

RLS is enabled on every private table. Household membership, explicit specialist assignment, and administrator checks govern access. Content editors can manage resources but cannot read household records. ETH-012 adds declared type, extension, filename, and size validation for private uploads. Security controls still planned before production include content-signature validation, malware scanning, production rate limits, CSRF review, headers, audit trails, retention/deletion workflows, backups/restoration testing, least privilege, and administrator MFA.

## Supabase credentials and privileged access

`NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` are the only Supabase values allowed in browser configuration. The publishable key is not a bypass credential: database and storage access must remain constrained by RLS and storage policies. `SUPABASE_SECRET_KEY` is validated only in a `server-only` module and is never imported by browser utilities.

The elevated client in `lib/supabase/admin.ts` bypasses RLS. It is permitted only for reviewed administrative or background operations that cannot run under the requesting user’s RLS context. Do not use it in Client Components, ordinary route UI, or normal user-request flows; do not log it, serialize it, or expose it through `NEXT_PUBLIC_` configuration. Local development must use a local Supabase project and synthetic data, never a production project or production credentials.

Professional review is required for threat modeling, retention periods, incident response, regional/privacy obligations, HIPAA/FERPA/COPPA applicability, legal copy, and production penetration testing. This foundation makes no compliance claim.

## ETH-008 authentication controls

Supabase email/password authentication uses cookie-based PKCE sessions. Server authorization uses verified JWT claims through `auth.getClaims()` rather than `getSession()`, client state, or user metadata. The confirmation callback validates either a PKCE code or approved token-hash type without logging the code, hash, callback URL, cookies, access tokens, refresh tokens, or passwords. All return destinations must be supported-locale relative paths, preventing open redirects. A successful recovery callback creates only a short-lived, HTTP-only, locale-scoped recovery-intent cookie; both the reset page and update action require it, and a successful update clears it.

Password-recovery responses are neutral to avoid account enumeration. `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` is the only Supabase credential available to browser code. `SUPABASE_SECRET_KEY` remains in the `server-only` elevated client for reviewed background or administrative work and is not used for ordinary sign-in, sign-up, or recovery. CAPTCHA, production rate-limit monitoring, template review, CSRF/CSP review, and administrator role-governance require follow-up security review before production use.

## ETH-009 household and role controls

Profiles are self-readable and users may update only their own non-privileged fields. Application roles live in a separate table with no ordinary user write policy. Household and membership visibility requires active membership, and removal immediately removes access. Direct client membership creation, role escalation, ownership transfer, restoration, and hard deletion are denied. The public household RPC never accepts an owner ID, role, or permission from its caller.

Security-definer Auth synchronization and RLS helper functions use fixed empty search paths and fully qualified database objects to avoid search-path and policy-recursion attacks. They read metadata only for display fields and never for authorization. The `private` helper schema is not exposed through the Data API; only narrowly needed execution rights are granted to authenticated users. A service-role client remains prohibited from member-facing request flows.

## ETH-011 dependent controls

Dependent information is household-scoped and may be sensitive. `dependents` forces RLS and grants no anonymous access or delete permission. Active members and viewers can query only active dependents in their active household. Owners and household administrators alone may insert, update, or archive records. The archive operation writes `archived_at`; a trigger then prevents subsequent editing or household/creator reassignment. The normal member UI always filters archived profiles, including direct profile routes. Owners and administrators retain database visibility of archived records only because PostgreSQL evaluates the select policy for an update's proposed row; this is needed for the authorized archive transition and is not exposed through the active UI. Removal from `household_members` immediately removes every dependent read/write permission.

The server action accepts only permitted form fields and derives the household and actor from verified claims plus the active membership. It returns localized generic errors, never raw database errors. No dependent action imports `lib/supabase/admin.ts`, serializes a server secret, or trusts a browser-provided household or role.

## ETH-012 document controls

`family-documents` is a migration-defined private Storage bucket with a 20 MiB limit and allowlist for `application/pdf`, DOCX, and `text/plain` where Storage supports them. It has no public object URLs, and document code never calls `getPublicUrl`. The application also validates the declared MIME type, extension, non-empty size, maximum size, and normalized filename before preparing an upload. These checks improve safety and usability but do not prove the file contents are safe: this issue does not implement content-signature validation, malware scanning, OCR, parsing, or background processing.

The prepare action derives the user and active household from verified server-side claims and membership. It does not accept a household ID, uploader, document ID, or path from the browser. The database trigger creates the document UUID and final path, `households/{householdId}/dependents/{dependentId|unassigned}/documents/{documentId}/{safeFilename}`, validates an optional dependent belongs to the same active household, and locks identity and file metadata after preparation. An owner, household administrator, or member can prepare a pending document; a viewer, removed member, unrelated user, or anonymous user cannot. Active household members can read non-archived metadata for their household. Owners, administrators, and an eligible original non-viewer uploader retain only the archived-row visibility PostgreSQL needs to authorize their archive transition; member UI does not expose archived rows as active documents.

Storage object policies require a matching pending document row and exact generated path for an upload. They permit only the original active non-viewer uploader to create that object, prevent upsert replacement and arbitrary moves, and grant no normal-user object update or delete policy. Read access requires the exact uploaded, non-archived document and active household membership; a user removed from the household immediately loses it. The archive action is limited to an owner, administrator, or the original uploader who remains an active non-viewer member. It sets the database archive state only; a future retention workflow must decide when, whether, and under what approval to physically delete the private object.

The browser receives only the path, document ID, and time-limited signed-upload token needed for the direct upload; it never sends the file body through a Server Action. Tokens are not persisted or logged. Supabase upload tokens are valid for two hours and cannot be individually revoked, so a token issued before removal or archive could still place an orphan object at its exact path until expiry; it cannot complete or be read through the app after the database authorization check fails. Completion rechecks the expected object metadata before changing a pending row to `uploaded`, and upload failures are represented as `failed` rather than success. Pending rows left after an interrupted browser session and any such orphan objects are not automatically purged in ETH-012; scheduled cleanup is a future operational task. The authenticated download route validates the UUID and RLS-visible active uploaded row, creates a 60-second signed URL, and redirects to it. Missing, archived, unauthorized, and cross-household documents have the same safe not-found response. No member document flow imports or exposes `SUPABASE_SECRET_KEY` or the administrative client, and server responses keep database and Storage errors generic.

## ETH-013 binder controls

The binder accepts no household ID from URL state. Its server-only query first derives the caller's verified active household and membership, then applies that household predicate before every metadata search, dependent, status, date, sort, count, and page operation. Query values are Zod-normalized: dependent IDs must be UUIDs and are accepted only when present in the active household's selectable dependents; filters use fixed allowlists; dates are strict calendar dates; page size is fixed; and sort values map to fixed `created_at`, `title`, and `id` fields. Invalid input is ignored or reset safely and never becomes a raw column or filter expression.

Metadata search is limited to title, normalized original filename, and category. The untrusted query is reduced to Unicode letter/number tokens before the server constructs its fixed PostgREST `ilike` expression, preventing punctuation from becoming filter syntax. The binder does not fetch every household document into a client, search file contents, log document metadata, create a public URL, import the administrative client, or generate a signed download outside the existing authorized route. Default results explicitly exclude archived rows; archive visibility, detail visibility, and dependent names remain RLS-governed. A generic archived-family-member label preserves document visibility without broadening profile/dependent access.

## ETH-014 processing controls

ETH-014 accepts processing requests only for active uploaded documents, and only from an owner, household administrator, or member. The database derives identity, household, eligibility, idempotency, and retry bounds; a browser cannot write `processing_status`, jobs, pages, chunks, or analyses. A private marker-backed transition helper prevents a forged direct document-status update. Queue and safe-status RPCs reveal only their minimum user-facing result, while job claim, completion, and failure RPCs are executable only by the service role.

The administrative Supabase client is confined to the server-only background worker. A distinct high-entropy `DOCUMENT_PROCESSING_SECRET` protects the internal batch route and is compared in constant time. It must not be reused from `SUPABASE_SECRET_KEY`, exposed through `NEXT_PUBLIC_`, placed in a query string, logged, or included in an error response. The route accepts no document identifier or body and returns only aggregate counts or a generic error.

The worker rechecks the trusted private bucket/path, declared type, and size before server-side download. TXT, DOCX, and PDF extraction are bounded and fail closed; DOCX external resource access is disabled, textless PDFs become `needs_ocr`, and no OCR provider runs. Raw parser, database, and Storage errors are mapped to a small fixed safe error-code/message set. It logs neither content, filenames, paths, signed URLs, secrets, nor raw errors. Pages and chunks force RLS and derive their read policy from the active uploaded unarchived parent document, so archive, removal, or cross-household access denial also denies derivatives. Extraction is stored for authorized future work only; ETH-014 does not render or search it in the member UI, place it in analytics, or use it for an unreviewed purpose.

## ETH-015 document-summary controls

ETH-015 permits a narrowly scoped, authorized runtime use of protected extraction to create a source-grounded summary. It does not change the upload/processing RLS boundary or make extraction generally browser-readable. Only an active owner, household administrator, or member can request or retry a summary; an active viewer can read a summary that is already accessible but cannot create provider cost. Anonymous users, removed users, unrelated households, archived documents, incomplete processing, failed processing, unsupported files, and `needs_ocr` documents are denied by server and database checks rather than hidden UI alone.

ETH-016 permits an equally narrow OCR fallback only for an active, uploaded, unarchived `application/pdf` document already marked `needs_ocr`. The queue function derives the actor, household, document, MIME type, and status in PostgreSQL; owners, administrators, and members may request it, while viewers, removed members, anonymous callers, unrelated households, non-PDFs, archived records, incomplete uploads, and completed/processing records are denied. `document_ocr_jobs` forces RLS and has no normal browser grants; normal users cannot claim jobs, write provider metadata, or insert pages/chunks. The service-role-only claim/fail/complete functions use a fixed empty search path, bounded leases/retries, and safe error codes without raw provider or renderer errors.

The OCR worker downloads only a revalidated private object and never creates a public or signed page-image URL. PDF page images exist in bounded server memory only; the application logs no PDF bytes, images, OCR text, storage paths, signed URLs, provider payloads/responses, API keys, or worker secrets. `OCR_PROVIDER`, `OCR_API_KEY`, and `OCR_MODEL` are server-only and must be complete together; `DOCUMENT_OCR_SECRET` is high-entropy, separately rotated, constant-time-compared, and never reused from the Supabase, processing, or summary secrets. The provider may make transcription errors. Its text is treated as untrusted data, never translated or used as instructions, and successful storage does not certify accuracy or provide legal, medical, educational, financial, or other professional advice.

The provider is invoked only from a server-only, provider-neutral module. `OPENAI_API_KEY` and `OPENAI_SUMMARY_MODEL` are server-only and fail closed when absent or incomplete. `DOCUMENT_SUMMARY_SECRET` is a distinct high-entropy invocation credential for the internal summary worker; it is compared safely, cannot be blank, and must not be reused from `SUPABASE_SECRET_KEY` or `DOCUMENT_PROCESSING_SECRET`. None of these values may use a `NEXT_PUBLIC_` name, enter a Client Component, query string, browser response, source-control file, or log. Provider SDKs, raw request bodies, raw responses, document content, summaries, source excerpts, secrets, signed URLs, and internal errors are not logged or returned to the browser.

Document text is untrusted data, not instructions. Protected prompts separate system instructions from source data, tell the model to ignore instructions contained in the document, prohibit secret disclosure, tool use, code execution, URL visits, authorization changes, and format changes requested by the document, and require controlled structured output. The application validates the provider result with a strict schema before it stores or renders it. It rejects unsupported languages, oversized fields/lists/excerpts, malformed sources, HTML/script output, and references outside the parent document. It never uses `dangerouslySetInnerHTML` for a summary.

Summary rows force RLS and remain parent-document scoped. Browser clients cannot directly insert, alter, claim, or complete them; service-role worker functions are not granted to normal clients. Source references are resolved against the authorized document's ordered pages/chunks before persistence, so the model cannot select another household's content or invent a database identifier. The UI renders only a short protected excerpt where needed for verification and never creates a public source URL. Archive or membership removal removes normal summary/page/chunk access immediately.

The summary is assistance, not a factual or professional guarantee. It may be incomplete when long-document limits apply, may contain mistakes, does not make medical diagnoses or legal conclusions, and must not replace review of the original document or qualified professional advice. OCR, image analysis, document chat, cross-document search, embeddings, vector search, provider tools, autonomous actions, public sharing, training, and fine-tuning remain out of scope.

## ETH-017 document-question controls

ETH-017 permits a bounded question about exactly one active, uploaded, completed private document. The Server Action validates only a UUID, fixed language, and trimmed 700-character question; it derives the active household context server-side and returns only localized generic failures. The request RPC locks the document and independently derives `auth.uid()`, household, non-viewer permission, document eligibility, duplicate/retry state, and the normalized question key. Browser-supplied identities, households, roles, ownership, provider information, source references, and status are ignored because no browser write policy or RPC argument accepts them.

`document_questions` forces RLS and can be selected only while an active household member may access the active completed parent document. An archive, membership removal, anonymous request, or other-household request therefore loses access immediately; inaccessible and missing records do not get distinguishable member-facing treatment. The worker-only claim, completion, and failure functions require `service_role`, fixed empty search paths, bounded leases, and fixed safe errors. Completion verifies each citation's page/chunk coordinate and excerpt belongs to the same parent document. The browser gets no raw provider/database error, source database ID, private path, signed/public URL, or worker secret.

`OPENAI_API_KEY`, `OPENAI_QUESTION_MODEL`, and `DOCUMENT_QUESTION_SECRET` are server-only. The secret is constant-time compared, must be at least 32 characters, protects only the aggregate internal question route, and must not be reused from `SUPABASE_SECRET_KEY`, processing, summary, or OCR secrets. Prompts treat question/document text as untrusted data, disable tools and provider storage, and instruct the model not to follow document-contained commands. The bounded answer is informational only, may contain errors, and must be verified against the original document; it is not legal, medical, educational, financial, or other professional advice.

ETH-019 extends the same provider and worker boundary with persistent household-shared chat. Conversations are accessible only through an active, uploaded, unarchived, completed parent document with searchable chunks; archive, removal, anonymous access, or another household fail closed and do not reveal whether a conversation exists. Server Actions accept only a target document/conversation/message UUID, controlled locale, bounded message, and UUID idempotency key. PostgreSQL derives all household, identity, role, ownership, sequence, and lifecycle state, rejects viewer writes and browser assistant/citation writes, and atomically prevents duplicate messages or concurrent assistant jobs. The worker receives only the current document's bounded source rows and the latest ten completed messages from the same conversation; earlier assistant text is context rather than evidence. It persists only safe errors and validated page/chunk coordinates, never provider payloads, prompts, source content logs, excerpts in the chat UI, signed URLs, or provider metadata. ETH-018 quality/review state is advisory only and cannot block chat; approval retains its limited household internal-use meaning.

## ETH-018 summary quality and review controls

ETH-018 evaluates only an accessible, active, uploaded, processed, completed summary through a security-definer RPC with a fixed search path. The caller supplies only a document UUID and controlled language; PostgreSQL derives `auth.uid()`, the active household, and the summary. No AI SDK, service-role browser client, provider call, new secret, source text log, raw evaluator error, source database ID, or signed URL is involved. Evaluation is stored separately from generation and returns only safe scores/checks/warnings to the server-rendered panel. It rechecks same-document page/chunk references and excerpt containment, so a tampered cross-document reference fails quality evaluation without exposing source content.

Review submission similarly derives the reviewer, household, and permission in PostgreSQL. Active viewers can read but cannot write; active members can report issues and edit their own pending feedback but cannot decide; only active owners/administrators can approve, reject, or request revision. Direct table grants are absent, immutable triggers prevent reassignment/forged IDs and final-review edits, and archive/removal/unrelated/anonymous access fails closed through parent-document RLS. “Approved” is a household internal-use label only; it never claims professional, clinical, medical, legal, provider, or accuracy verification. ETH-018 does not regenerate content, add chat/OCR/page-citation UI, or use AI as a judge.

## ETH-020 citation evidence controls

ETH-020 does not trust a browser-supplied page, chunk, excerpt, household, storage path, signed URL, or source owner relationship. Its one evidence RPC accepts only a document UUID, fixed persisted owner type, owner UUID, and bounded citation index. With a fixed empty search path, PostgreSQL first requires `auth.uid()` and active household membership, then verifies the active uploaded completed document, binds the owner to that same document and household, validates the persisted source-reference JSON, and re-resolves page/chunk provenance against the parent. Missing, malformed, stale, archived, removed-member, and cross-household inputs all return the identical unavailable shape. The function never raises a differentiating member-facing error or returns source IDs, paths, raw derivative rows, signed URLs, or an unbounded excerpt.

ETH-023 grants resource management access only to the global `administrator` role. It is deliberately not a household permission and does not grant any household, dependent, document, roadmap, reminder, source, or private-schema access. RLS exposes public readers only to published, unarchived resources with approved canonical-English content; drafts, reviews, rejection notes, audit records, administrator IDs, and other locales fail closed. Security-definer RPCs use a fixed empty search path, derive the actor from `auth.uid()`, validate bounded content and state transitions, permit administrators to approve their own submitted resource, and store audit metadata without resource body snapshots.

Normal browser roles have no `select` grant on `document_pages` or `document_chunks`; server-only workers retain the separate service-role source-material boundary. The member evidence sheet receives only the verified short excerpt and display-safe metadata after the Server Action validates its input. The PDF viewer route repeats owner-bound evidence validation before querying the active parent document and creates a 60-second private signed URL only for the stored PDF page; DOCX/TXT use logical sections and cannot construct a page target. There is no public Storage URL, raw database error, source text logging, provider call, or special cross-household administrator bypass. Citation evidence is read-only and does not alter summaries, answers, chat, document state, or review decisions.

## RBT training progress controls

The RBT lesson is an educational resource whose static source tree contains no user data and makes no network request. The original supplied HTML is kept outside the runtime render path for provenance; its inline script is not served or executed. A signed-in user may record only their own last viewed and completed fixed section keys through `public.record_training_progress(text, boolean)`. The function obtains `auth.uid()` itself, validates the allowlist, and returns only safe progress fields. `training_progress` forces RLS, grants no anonymous access, has no delete policy, and contains no household, dependent, document, score, credential, or clinical information. Browser code receives no service key and cannot supply a `user_id`; direct foreign-row insertion and updates are denied by RLS.
