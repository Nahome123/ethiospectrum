# Data model

## ETH-027 appointments

ETH-027 reuses `public.appointments` and adds `support_thread_id`, `proposed_by`, `proposed_local_datetime`, `timezone`, `duration_minutes`, `modality`, a server-controlled `version`, consent fields (`consented_by`, `consented_at`, `consent_copy_version`), decline, cancel, and complete actor-and-timestamp pairs, an allowlisted `cancellation_reason`, `supersedes_appointment_id`, and `idempotency_key`. The existing `start_time`, `end_time`, `meeting_url`, and `status` columns are reused, with `status` moving to `proposed`, `scheduled`, `declined`, `cancelled`, `completed`. A lifecycle constraint ties each status to its required actor and timestamp fields, and a modality constraint enforces that a video appointment carries a bounded HTTPS link while a phone appointment carries none. A partial unique index allows only one `proposed` or `scheduled` appointment per request, and idempotency is unique per request, proposer, and key.

`public.appointment_events` is append-only, holding appointment, request, household, actor, an allowlisted `proposed`/`accepted`/`declined`/`cancelled`/`completed` action, an optional controlled reason, the appointment version, and bounded `safe_metadata` that carries only category-style values, never a meeting URL, message body, or household-private record. An immutability trigger rejects updates, RLS is forced, and reads are limited to active household members, the currently assigned specialist, and platform administrators. `private.appointment_markers` is a no-grant transaction marker: without it the integrity trigger rejects any appointment write, including from an elevated connection.

## ETH-026 specialist assignment

ETH-026 reuses `support_threads.specialist_id` as the authoritative active assignment and adds `specialist_assigned_at`, `specialist_assigned_by`, a non-null `assignment_version` defaulting to zero, and `assignment_updated_at`. A check constraint keeps the specialist and its metadata consistent — all present or all absent — so a terminal request can never retain a half-cleared assignment, and a partial index on `(specialist_id, updated_at desc)` where the request is open matches exactly the rows a specialist may read. `support_messages` gains a server-controlled `author_kind` (`caregiver` or `specialist`) with existing rows backfilled as `caregiver`; the message-integrity trigger additionally requires that a `specialist` message's sender is the request's current specialist on an open request.

`public.support_request_assignment_events` is a new append-only table holding thread, household, specialist, actor, an allowlisted `assigned`/`revoked` action, the assignment version, an optional controlled reason (`administrator_revoked`, `request_closed`, `request_cancelled`), bounded `safe_metadata`, and a timestamp. It stores no message body, raw request object, or household-private content; an immutability trigger rejects updates, RLS is forced, and only the platform-administrator role may select. Assignment history survives revocation, so a request's full grant timeline stays auditable. `private.support_assignment_markers` is a no-grant transaction marker table: the thread-integrity trigger rejects any change to assignment columns without a matching marker, so even an elevated connection cannot forge an assignment or version. `household_specialists` keeps its original shape and is neither read nor written by ETH-026.

## ETH-025 support requests

ETH-025 reuses `public.support_threads` as the support-request record and extends it with a trusted `created_by`, a trimmed 5–120 character `subject`, an allowlisted `category` (`general`, `benefits`, `education`, `healthcare_navigation`, `therapy_support`, `housing`, `transportation`, `documentation`, `other`), a `preferred_language` (`en`/`am`/`es`), server-generated `expectations_acknowledged_at` and bounded `expectations_copy_version`, a server-controlled integer `version`, nullable `closed_by`/`closed_at`/`cancelled_by`/`cancelled_at`, and a creator-scoped `idempotency_key`. `status` is `open`, `closed`, or `cancelled` with a lifecycle constraint tying each terminal status to its actor/timestamp pair. The legacy nullable `specialist_id` remains dormant: an integrity trigger rejects introducing or changing it, no payload exposes it, and ETH-026 owns its future use. The same trigger makes identity and content columns immutable, blocks every update to closed or cancelled rows (including reopening), and bounds version changes.

`public.support_messages` gains a denormalized `household_id` and message `idempotency_key`; content is trimmed and bounded at 1–3,000 characters (the creation function enforces 20–3,000 for the initial description and 1–2,000 for follow-ups). A trigger validates thread/household consistency and rejects all updates, and no browser write, update, or delete grant exists. `public.support_request_events` is a new append-only audit table with thread/household references, `actor_user_id`, an allowlisted `created`/`message_added`/`closed`/`cancelled` action, nullable from/to statuses, the request version, bounded `safe_metadata` (category, preferred language, message sequence — never message bodies, raw requests, tokens, or secrets), and a creation timestamp; an immutability trigger rejects updates. All three tables force RLS with select-only policies for active household members and platform administrators; unique indexes enforce creation/message idempotency and partial indexes support household activity and open-request counts.

## Member resource discovery

`resources.resource_type` is an allowlisted discovery classification (`article`, `guide`, `video`, `template`, or `event_recap`), and nullable `featured_rank` controls deterministic administrator curation. Both changes share the resource optimistic version and append a safe `discovery_metadata_updated` audit event. `resource_bookmarks` has a composite user/resource key, forced RLS, and an own-row read policy; browser writes are revoked and occur only through the identity-derived bookmark function.

Catalog and detail functions return only published, unarchived resources with approved canonical English, selecting a current approved Amharic or Spanish translation before localized English fallback. Account access records decorate results as “For You” assignments. Roadmap links use existing `roadmap_items.source_type='resource'` and `source_id`, are creator/resource idempotent, and copy only the selected reviewed title, summary, and category into the caller’s active household roadmap.

## ETH-024 resource translations

`resource_translations` remains one row per resource and locale. ETH-024 adds submitter timestamps, source English version, and creator/updater fields while retaining `draft`, `in_review`, and `approved` states. Non-English mutation is limited to `am` and `es`. `resource_translation_audit_events` is append-only and stores actor, safe transition metadata, and version numbers only. Public eligibility requires a published parent, approved English, approved requested translation, and matching source version.

## ETH-021 household roadmap

`roadmaps` has one optional default row per household. `roadmap_items` belongs to that household and roadmap and records a bounded title/description, allowlisted category/priority/status, calendar due date, optional active dependent, optional household-member assignment, trusted creator, server-owned completion timestamp, archive timestamp, deterministic sort order, update timestamp, and creator-scoped idempotency key. Integrity triggers ensure parent household consistency, immutable ownership links, and valid dependent/member references while allowing historical archived records to remain readable. The existing `reminders` table and its foreign key are intentional future groundwork and ETH-021 neither reads nor changes them.

`auth.users` is the identity source. `public.profiles` stores only editable display fields, locale, timezone, and timestamps; it does not duplicate passwords, sessions, tokens, or email. The Auth trigger creates missing profiles and `public.user_roles` rows with the default `member` role, and the migration backfills existing Auth users without changing existing roles.

`public.user_roles` isolates privileged application roles from user-editable profiles. `public.households` uses a soft-delete timestamp, a primary owner, and a creator. `public.household_members` joins an Auth user to a household with `owner`, `administrator`, `member`, or `viewer` permission and an `active`, `invited`, or `removed` lifecycle. An owner membership must be active. Household creation inserts the household and owner membership together through the database function; invitations and ownership transfer remain deferred.

ETH-018 adds `document_summary_evaluations`, one current row per `document_summaries` row, and `document_summary_reviews`, one row per summary/reviewer. Both store their document and household only as trigger-validated denormalized foreign keys; they cannot be moved to another summary, document, household, or reviewer. An evaluation has a separate `pending`, `completed`, or `failed` state, a fixed evaluation version, bounded 0–100 component scores, bounded JSON checks/warnings, and no provider payload or document content. A review has controlled `review_in_progress`, `approved`, `rejected`, or `needs_revision` status; nullable 1–5 ratings; the fixed issue-category allowlist; trimmed 2,000-character feedback; and a submitted timestamp for final decisions. Forced RLS allows only active members who can read the active parent summary to select either table; direct browser writes are revoked.

`public.dependents` belongs to exactly one household. ETH-011 adds a non-null `created_by` Auth-user reference and nullable `archived_at` timestamp, while retaining only first name, optional last/preferred name, optional birth year, optional school district/grade level, and limited notes. Database constraints trim text, reject blank required names and oversized fields, and keep the birth year between 1900 and the current year. A trigger sets `created_by` to the authenticated actor on insert, prevents later household/creator reassignment, and makes archived records immutable. The active-list index covers `household_id, created_at` where `archived_at is null`. A dependent with linked document metadata cannot be hard-deleted; normal workflows archive it instead so document assignment remains immutable.

ETH-012 makes `public.documents` the metadata authority for private uploads. A row has its UUID, household and optional dependent, authenticated uploader, trimmed title, normalized original filename, fixed `storage_bucket` (`family-documents`), generated `storage_path`, declared MIME type, file size, optional category and detected language, processing status, upload status, timestamps, and nullable `deleted_at`. Title and filename have bounded lengths; MIME type is restricted to PDF, DOCX, and TXT; file size must be greater than zero and no more than 20 MiB; an optional category is one of `education`, `health`, `legal`, or `other`; and `(storage_bucket, storage_path)` is unique. The active-list and dependent indexes support household document pages without including archived rows.

`upload_status` is `pending`, `uploaded`, `failed`, or `archived`. `processing_status` begins as `not_started`; it does not imply OCR, extraction, scanning, or AI processing. A database trigger derives `uploaded_by`, forces the private bucket, normalizes the filename, generates the UUID-backed storage path, sets audit timestamps, verifies that an optional dependent is active in the same household, and makes identity and file metadata immutable after preparation. A pending row can become uploaded or failed only by its original active non-viewer uploader; managers may archive records but cannot finalize another member's upload. Archive sets both the archived status and a server-owned `deleted_at`; normal member workflows never hard-delete a document or its object. Pre-ETH-012 rows without lifecycle metadata are marked `failed` fail-closed rather than treated as verified private uploads, so a hosted rollout must inventory and deliberately migrate or re-upload any legacy document records.

ETH-013 uses those existing `documents` fields for metadata-only binder search, filters, sorting, and pagination; it does not add a migration. The binder treats `created_at` as the upload-record timestamp used for date filtering and ordering, not as a guaranteed completed-upload timestamp. Existing active-household, active-uploaded, and active-dependent indexes remain in place; no full-text, trigram, category, status, or additional pagination index was added without a measured need. Default binder queries require `deleted_at is null`; an explicit `upload_status = archived` view is still constrained by document RLS. Active dependent options exclude `archived_at` rows, while already linked document metadata remains immutable and may use a neutral archived-dependent label when profile RLS withholds the name.

ETH-014 makes `processing_status` an explicit controlled lifecycle: `not_started`, `queued`, `processing`, `completed`, `failed`, `unsupported`, or `needs_ocr`. A trigger rejects direct status changes; narrowly granted security-definer queue/worker helpers use a private transaction marker and an allowlisted transition graph. `public.document_processing_jobs` has exactly one row per document, a queued/processing/terminal job state, a maximum of three attempts, availability/lease timestamps, a bounded worker identity, and a fixed safe error-code/message surface. Active queue/archive work changes the job state atomically, while the document archive lifecycle remains in `upload_status` and `deleted_at`.

ETH-016 adds `public.document_ocr_jobs`, separately keyed one-to-one to a document so the original extraction job can retain its `needs_ocr` origin. An OCR job has the controlled `queued`, `processing`, `completed`, `failed`, or `cancelled` state; bounded attempts; availability, lease, start, completion, and failure timestamps; safe provider/model identifiers; and a fixed safe error-code/message surface. It force-enables RLS with no normal browser table grants. Narrow security-definer functions derive request authorization, return safe member-facing status only, atomically claim through `SKIP LOCKED`, fail a worker lease, and atomically replace pages/chunks during completion. `needs_ocr → completed` is valid only within that protected completion transaction after non-empty, bounded, ordered page/chunk output validates. OCR failure leaves `documents.processing_status = needs_ocr`; archive cancels active OCR work.

`public.document_pages` stores non-null extracted text plus a matching character count. `public.document_chunks` stores deterministic page/chunk indexes, a parent page reference, matching character count, and optional positive token estimate. The processing boundary validates worker JSON row shapes, page/chunk uniqueness, page-to-chunk parent consistency, and bounded output before inserting anything; every new or updated chunk is additionally capped at 1,200 characters. Jobs, pages, chunks, and analyses force RLS. Normal browser clients cannot query jobs, pages, chunks, or write any derivative; the service-role worker retains its reviewed source-material path. ETH-020's `get_document_extraction_availability` and `get_document_citation_evidence` functions return only derived availability or one verified bounded evidence record after active household/document/owner validation. The existing vector field remains dormant: ETH-014 writes no embeddings and exposes no content search.

ETH-015 adds the dedicated `public.document_summaries` table for source-grounded, language-specific summaries. It has an ID, trusted `document_id` and `household_id`, controlled language, lifecycle status, nullable summary text and structured result, bounded source-reference JSON, `source_coverage` (`full` or `partial`), safe provider and model identifiers, prompt version, trusted requester, request/start/completion/failure timestamps, a safe error code, and normal creation/update timestamps. It does not store an API key, signed URL, complete prompt, raw provider request/response, or a browser-provided household, actor, source ID, provider, model, prompt version, or status.

Summary status is distinct from both upload and processing status: `queued` waits for the protected worker, `generating` holds a bounded worker lease, `completed` has validated structured output and resolved sources, and `failed` holds only a safe retryable outcome. A unique active document/language path prevents duplicate work; completed summaries may be reused and failed summaries may be retried within bounded worker policy. Indexes support household/document/language reads and ordered queued-job claims. The existing updated-at trigger pattern applies to the summary table.

`document_summaries` forces RLS. Read access derives from the active, uploaded, unarchived parent document and active household membership, so an archive, removal, or cross-household denial immediately hides it. Normal authenticated clients have no direct summary write, claim, or completion privilege. Controlled security-definer functions use a fixed empty search path, derive trusted identity and household context, and reserve worker functions for the service role. Source references are stored only after validating that every referenced page/chunk belongs to the same parent document; excerpts are short bounded text for protected display, not public links or a replacement copy of the document.

ETH-017 adds `public.document_questions`, a document-scoped, language-specific question queue. Each row stores a trimmed bounded question, a derived lowercase same-document idempotency key, trusted document/household/requester references, a `queued`/`answering`/`completed`/`failed` lifecycle, a concise nullable answer, up to three validated source-reference excerpts, bounded source-coverage/call metadata, lease timestamps, and only fixed safe failure codes. The unique `(document_id, language, question_normalized)` key prevents duplicate concurrent work without treating it as chat history. RLS is forced and inherited from the active completed parent document; normal browser roles receive no table grant and use only a narrow safe-read RPC, while request/claim/complete/fail remain separately restricted. A completion function verifies every cited page/chunk and excerpt belongs to the same document before persistence. Archiving clears active answer work and makes rows inaccessible immediately.

ETH-019 adds `public.document_chat_conversations` and `public.document_chat_messages`. A conversation has an immutable trusted document/household/creator, one fixed `en`/`am`/`es` language, a deterministic first-message title, activity timestamps, and a creator/document-scoped creation idempotency key. Messages have immutable conversation/document/household links, an ordered sequence, a bounded user or assistant role, controlled `pending`/`generating`/`completed`/`failed` lifecycle, bounded attempts/leases, and an optional user idempotency key. A unique partial index permits only one active assistant response per conversation. Completed assistant messages store a controlled result type and up to three structured page/chunk coordinates; no source excerpt is duplicated for chat. Security-definer RPCs atomically create/send/retry and validate document availability, active membership, non-viewer role, parent links, sequence order, and citation coordinates. All normal tables force RLS and direct browser writes are absent.

ETH-020 adds no table. It reuses each persisted output's source-reference JSON and exposes `get_document_citation_evidence(document_id, owner_type, owner_id, citation_index)`. The function accepts only the three owner allowlist values `document_summary`, `document_qa_answer`, and `document_chat_message`; validates a 0-143 index; binds the owner to the active uploaded completed document and same household; resolves the referenced page/chunk back to that document; and returns a bounded Unicode excerpt, one-based PDF page or logical section number, availability, PDF-navigation eligibility, and partial-coverage state. It uses a single unavailable response shape for invalid, stale, archived, missing, removed, and cross-household requests. No source row identifier, chunk index, storage path, signed URL, raw page, or raw chunk is returned.

The trusted object-path shape is `households/{householdId}/dependents/{dependentId|unassigned}/documents/{documentId}/{safeFilename}`. The browser cannot choose any of its trusted IDs or supply a storage path. Document pages, chunks, embeddings, and analyses must derive access from their parent document, so a user denied the document is denied every derivative. `vector(1536)` is a planned embedding storage shape; dimension must be reviewed alongside the chosen model.

`public.training_progress` is an independent, user-owned reading-progress table for the fixed `rbt-errorless-teaching-intensive-teaching` course. Its unique `(user_id, course_key)` pair holds a deduplicated allowlist of completed section IDs, an allowlisted last-viewed section, start/update timestamps, and an all-sections-only completion timestamp. It contains no household, dependent, document, score, credential, or clinical data. RLS is forced: authenticated users can select, insert, and update only their own row, while the `record_training_progress` security-invoker function derives the caller from `auth.uid()` and rejects unknown section IDs.

ETH-023 extends `resources` with actor/timestamp audit fields, first-publish immutability, an optional creator-scoped idempotency key, archive state, and an optimistic integer version. It extends `resource_translations` with review timestamps, a bounded rejection note, and its own version; ETH-023 creates and edits only the required `en` record. `resource_audit_events` is append-only workflow metadata without body snapshots. The public catalog is derived from `published` resources with an approved canonical-English translation; administrator-only functions derive the actor from `auth.uid()` and never take an author, reviewer, publisher, role, or household identifier from the browser.
